Suppose your app has accepted a Dash payment. Dash Core records the transfer, but the app may still need to remember a delivery status, a username, or a note. Those records aren't payments, and putting them in one company's private database would return control of the app to that company.

Dash Platform fills that gap. It gives applications a network-hosted place for structured data, with shared rules for what may be stored and signed authorization for changes. Your frontend and business logic still run where you choose; Platform takes the job of keeping the application's shared records.

## The record after the payment

Start with a profile that contains a display name and a short biography. In a conventional app, you might store it as a row or JSON object in a database run by the app's operator. On Platform, the current profile lives in **Drive**, Platform's storage component. Drive holds the network's current **Platform state**, the data Platform currently recognizes. Within that state, each registered data contract has a separate application state.

That location changes who the app has to trust. The operator doesn't keep the only authoritative copy in a private database. Apps can read the shared state from the Platform network, so another client that understands the same application data can query it too.

Platform doesn't accept an arbitrary JSON object just because a client sends one. Before the profile can exist, the application needs a **data contract**: a registered description of the record types it uses, their fields, and the rules those records must satisfy. You can think of it as the schema for the application's part of Platform state.

The profile itself is a **document**, meaning an application record associated with that contract. A document carries the application's fields along with Platform fields such as its identifier, document type, revision, contract identifier, and owning identity. When a requested write doesn't match the contract's schema, Platform rejects it.

This gives the storage model a useful split:

- The data contract says what a valid record looks like.
- The document is the record currently stored in Drive.

## A valid record still needs an author

A matching schema answers "is this shaped correctly?" It doesn't answer "who asked for this change?"

A Platform **identity** is a persistent network account with public keys that Platform uses to verify its signatures. To create or change Platform state, an identity submits a signed <Term id="state-transition">state transition</Term>. The signature proves which identity authorized the request; Platform then checks that request against the existing record and its data contract.

For an ordinary mutable document, the current owner controls replacement and deletion. The contract still sets the boundaries. It can make a document type immutable, meaning it can't be updated, or prevent deletion; even its owner can't perform an operation the contract forbids. Creation has separate contract rules and may be open to anyone, limited to the contract owner, or disabled.

Return to the profile. If identity A owns it, identity B can't simply replace the biography with different text. Identity A must sign the replacement, the updated profile must still match the schema, and the contract must permit updates. Authorization and contract rules are both checked.

The contract has an owner too: the identity that registers it. Only that identity may submit compatible updates to the contract schema. Application records and the rules for those records therefore have related but distinct ownership.

## Pick the layer from the request

Once you know what Platform stores, choosing between Core and Platform becomes a question about the requested feature rather than a question about which SDK sounds more interesting.

| Feature request | Right tool | Reason |
| --- | --- | --- |
| "Let a customer pay 2 DASH at checkout." | Dash Core | The feature only sends and receives Dash. |
| "Give each user a profile that its owner can update and other clients can query." | Dash Platform | The feature needs shared application records and identity-authorized changes. |
| "Attach a readable name to a Platform identity." | Dash Platform | Names and identities are Platform application state, not Core payments. |
| "Run arbitrary user-written programs on the network." | Not Platform's documented data model | Platform accepts schema-governed state changes rather than arbitrary deployed programs. |

The short routing rule is: **use Core for Dash payments alone; use Platform when the feature needs shared, queryable application records, identities, or names.** One product can use both. A shop could take payment through Core while keeping an identity-owned order record on Platform.

Don't send every backend field to Platform. A local cache, temporary UI preference, or secret that one operator alone should hold doesn't become better merely because a network stores it. Platform answers the narrower need for shared application state whose valid changes shouldn't depend on one database administrator.

## A name is application data

The <Term id="dpns">Dash Platform Name Service (DPNS)</Term> shows what becomes possible once records and identities share a network. DPNS registers human-readable names and associates them with Platform identities. Dash Core alone can move Dash, but it doesn't provide this shared name registry.

The useful part isn't only that a name looks friendlier than an identifier. Different clients can consult the same Platform state, and a name's association belongs to an identity rather than to an account row controlled by one app operator. That's a concrete application you couldn't build on Core's payment ledger alone.

Dashnote supplies another example. Its users can create, edit, and delete their own notes, while other identities can browse those notes without gaining permission to change them. The familiar app behavior comes from the same model as the profile: contract-defined documents in Drive, ownership by identities, and signed requests for changes.

## The build order follows ownership

The hands-on path starts by connecting to the network, then creates and funds an identity. That identity can register a name and later own a data contract. Once the contract exists, documents can be created, queried, changed, transferred, and purchased; token work follows those document operations.

That order isn't arbitrary. A document needs a registered contract, and the contract needs an identity to own it. Rather than inventing a single named product, the exercises build each dependency in sequence so the same pieces can later support a profile, notes app, registry, or another record-based application.
