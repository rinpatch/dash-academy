Dash has two connected chains with different responsibilities. **Dash Core** is the layer 1 blockchain for Dash transactions. **Dash Platform** is a layer 2 state chain for application data.

Understanding that split is the key to understanding finality on Dash: Core transactions and blocks are protected by InstantSend and ChainLocks, while Platform blocks become final through Tenderdash consensus.

## Learning objectives

By the end of this lesson, you will be able to:

- identify the distinct roles of Dash Core and Dash Platform;
- explain how Long-Living Masternode Quorums support both layers;
- distinguish an InstantSend transaction lock from a ChainLock;
- explain why Tenderdash—not InstantSend or ChainLocks—finalizes Platform blocks.

## Two connected chains

| | Dash Core | Dash Platform |
| --- | --- | --- |
| Layer | Layer 1 | Layer 2 |
| Primary responsibility | Dash transactions, Proof of Work, masternodes, and quorum commitments | Application state and structured data |
| Unit submitted by a client | Transaction | State transition |
| Finality path | InstantSend for transaction inputs; ChainLocks for blocks | Tenderdash consensus for Platform blocks |

On Platform, developers define application data with schemas and submit signed **state transitions** that change that data. They do not deploy arbitrary user-written code for the network to execute. **Drive** validates and stores Platform state, which applications query through contract-defined indexes, while **DAPI** gives clients decentralized access to Platform data and the Core blockchain.

Platform can read Core state, but the relationship is one-way: Core does not depend on or need to know about the Platform chain. That lets Platform add application capabilities without making Core responsible for application data.

<Callout type="info" title="A useful mental model">
Core secures value and the layer 1 history. Platform reaches its own consensus about application state. The layers share masternode-based infrastructure, but they are not one chain and do not use one finality rule.
</Callout>

## Quorums: shared infrastructure

A **Long-Living Masternode Quorum (LLMQ)** is a deterministic subset of Dash's masternode list. Its members establish shared signing material through distributed key generation. When enough members sign the same consensus message, their signature shares can be combined into one compact BLS threshold signature that other nodes can verify.

“Quorum” does not mean one permanent committee handles every decision. Dash defines different quorum types and configurations for different features, including ChainLocks, deterministic InstantSend, and Platform. Platform also rotates its active validator set among Platform quorums.

This gives the layers a common foundation:

1. The deterministic masternode list is maintained on Core.
2. Quorums are selected from that list, and their commitments are recorded on Core.
3. Feature-specific quorums produce threshold signatures for their assigned work.

Shared quorums connect the systems. They do **not** make InstantSend, ChainLocks, and Tenderdash interchangeable.

## Core finality: InstantSend and ChainLocks

Core uses two complementary mechanisms at different levels.

### InstantSend locks transaction inputs

For a qualifying Core transaction, InstantSend automatically attempts to lock its inputs. Quorums conduct the signing sessions and broadcast a verifiable transaction-lock message. A conflicting transaction cannot validly spend those locked inputs, so a recipient can gain confidence before waiting for several mined blocks.

The important unit is the **transaction input**. InstantSend does not finalize a Platform block.

### ChainLocks finalize Core blocks

For each Core block height, members of the ChainLocks quorum sign the first block they observe extending the active chain. When the threshold signature is recovered and broadcast, nodes reject competing blocks at that height and any descendants of those competing blocks. This prevents reorganizations below the locked Core block.

The important unit is the **Core block**. ChainLocks and InstantSend also reinforce each other: a ChainLock is attempted only after every transaction in the block has an InstantSend lock. If necessary, the network establishes those transaction locks retroactively before ChainLock creation.

| Mechanism | Protects | Result |
| --- | --- | --- |
| InstantSend | Inputs of a qualifying Core transaction | Conflicting spends of those inputs are rejected |
| ChainLocks | A Core block at a particular height | Competing Core blocks at that height and any descendants of those competing blocks are rejected |

## Platform finality: Tenderdash

Platform needs consensus over ordered state transitions and the resulting application state. Its rotating validator sets run **Tenderdash**, Dash's pBFT-based adaptation of Tendermint.

The flow is:

1. A validator proposes a Platform block containing state transitions.
2. The active validator quorum validates the block and votes through the Tenderdash rounds.
3. Once at least two-thirds plus one of the validator set accepts the block, it is committed and final.

A final Platform block is not later reorganized. Tenderdash uses the LLMQ system's BLS threshold signatures, so the validators' approval can be represented compactly. The quorums are drawn from Dash's deterministic masternode list and committed on the Proof-of-Work-secured Core chain. Platform therefore combines its own rapid BFT finality with validator membership rooted in Core state.

Platform data is also designed to be verifiable. You will explore how that verification works in the later Proofs lesson.

<Callout type="warn" title="Keep the finality paths separate">
InstantSend and ChainLocks protect activity on Core. Tenderdash quorum consensus finalizes Platform blocks. LLMQs participate in all three systems, but that shared infrastructure does not mean Core mechanisms directly finalize Platform blocks.
</Callout>

## How Core evidence crosses into Platform

Platform can consume proof that securely establishes a Core asset lock without borrowing Core's finality rule for its own blocks.

Identity funding is a concrete example. A user first locks Dash in a Core asset-lock transaction. Platform can accept either an InstantSend proof for fast confirmation or proof that the transaction appears in a ChainLocked Core block. The user then references that proof in an identity-creation state transition, and the locked value becomes Platform credits after fees.

InstantSend supplies fast transaction-lock confirmation; a ChainLock establishes Core block finality once the transaction is included in a ChainLocked block. In either case, the proof establishes the asset lock securely. Tenderdash still decides when the Platform state transition enters a final Platform block.

## What you accomplished

You can now trace Dash's two finality paths. InstantSend protects Core transaction inputs, ChainLocks finalize Core blocks, and Tenderdash finalizes Platform blocks. You also understand how feature-specific LLMQs provide shared threshold-signing infrastructure without collapsing those mechanisms into one rule.
