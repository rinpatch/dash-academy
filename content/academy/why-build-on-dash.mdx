## Learning objectives

By the end of this lesson, you will be able to:

- identify the parts of an application that benefit from Dash payments or verifiable shared state;
- distinguish Dash, Platform Credits, fungible tokens, and document-based NFTs;
- explain the privacy boundary between Core payments and Platform data; and
- describe what the Dash DAO governs—and what it does not.

The useful question is not “Should this entire application be on a blockchain?” It is **which parts need independent verification, shared ownership, or native settlement?** A product can use Dash for those parts and keep private data, specialized computation, and ordinary web services elsewhere.

## Start with the trust problem

Dash is a strong fit when users or independent clients need to agree on value, identity, ownership, or application state without treating one company’s database as the final authority.

| Need | Where Dash helps |
| --- | --- |
| Pay or receive digital money | Dash Core provides the Dash asset and payment settlement. The network attempts to InstantSend-lock qualifying transactions, while ChainLocks make the selected chain unambiguous. |
| Share structured application records | Platform validates data against contracts, stores finalized state across the network, and can return cryptographic proofs with queries. |
| Give users portable identities and names | Platform identities sign actions; DPNS associates human-readable `.dash` names with identities. |
| Create application assets | Platform supports configurable fungible tokens and unique, document-based NFTs. |

Platform is less suitable when the main requirement is arbitrary on-chain program execution. Developers define schemas and submit supported state transitions; they do not deploy unrestricted application code to run on every node.

It is also a poor replacement for unrestricted analytics. Document filtering and sorting must follow indexes defined in the data contract. A reporting workload with unpredictable, ad hoc queries will usually still need an off-Platform index or analytics system.

<Callout type="info" title="Use the smallest decentralized surface that solves the problem">
A marketplace might keep search recommendations and private support messages in conventional services while putting payments, listings, and ownership records on Dash. A hybrid architecture is often the best fit.
</Callout>

## Choose the right value primitive

“Value on Dash” can refer to several different things. They are not interchangeable.

| Primitive | What it is | Typical use |
| --- | --- | --- |
| **Dash** | The native asset on the Core blockchain | Payments, settlement, and the source of value used to create Platform Credits |
| **Credits** | Platform’s accounting unit for fees, derived from Dash | Paying the cost of Platform activity such as state transitions and storage |
| **Fungible token** | A developer-configured asset declared in a Platform data contract | Rewards, memberships, tickets, loyalty points, or other interchangeable units |
| **Document-based NFT** | A unique Platform document with ownership behavior | Collectibles, certificates, unique game items, or marketplace assets |

The documented conversion is **1 Dash = 100,000,000,000 Credits**. That does not make Credits another general-purpose app token. Credits account for Platform costs; application tokens express rules and value chosen by a developer. A configured token sale may accept Credits, but the purchased token remains a separate asset.

Platform’s fungible-token features are protocol supported rather than arbitrary smart-contract code. A token can be configured for actions such as minting, transferring, burning, freezing and thawing, distribution, access control, and direct purchase. That is useful when the built-in model matches the product. If the product needs execution rules the protocol does not provide, Platform alone is not the right runtime.

## Build for people: usernames and unique assets

A Platform identity is a cryptographic actor, not a friendly display name. DPNS adds the human layer by associating a `.dash` name—such as `alice.dash`—with an identity. The identity controller proves control when signing interactions. This can make an account or payment experience easier to recognize without making names secret or replacing careful authorization.

Dash Platform NFTs use documents as their foundation. Each document has a unique identifier and can contain indexed application data. A contract can define whether those documents may change, be deleted, or transfer to another owner. Platform also supports protocol-integrated purchase behavior.

That document model is a good fit when a product needs a verifiable unique record with ownership. It is not the same as issuing one unit of a fungible Platform token: fungible units are interchangeable, while each NFT document is individually identifiable.

## Treat privacy as a design decision

Dash does not make every payment and application record private by default.

On Core, **CoinJoin** is a non-custodial wallet process that can improve payment privacy by mixing denominated inputs with other participants. It involves preparation, sessions, and fees. It is not automatic encryption for every Dash transaction.

On Platform, DAPI uses TLS to protect data while it travels between a client and a node. TLS does not make stored fields confidential. Platform state is replicated and designed to be queried and verified, so an application should not place plaintext medical details, private messages, secret credentials, or similar sensitive content there.

If an application needs both verifiability and confidentiality, store only the necessary commitment or public record on Platform and keep sensitive content encrypted or off Platform. Encryption also requires an intentional key-management and recovery design; it is not supplied merely by using TLS.

<Callout type="warning" title="Public integrity is not private storage">
Cryptographic proofs answer “Does this response match Platform state?” They do not answer “Can nobody else read this field?”
</Callout>

## Understand the DAO boundary

Dash’s decentralized autonomous organization governs the **Dash network and treasury**. A portion of the block subsidy funds proposals, and qualifying masternodes vote on how treasury funds are distributed. This can matter to a builder because the ecosystem has a network-level process for funding work that advances Dash.

Building an application on Dash does not automatically give that application its own DAO. Product permissions, upgrades, moderation, and community voting still need an application-specific governance design. Do not confuse access-control groups for a Platform token—or any other app rule—with the governance of the Dash network itself.

## Apply the fit test

For each proposed feature, ask three questions:

1. Does it need native Dash settlement or state that independent clients can verify?
2. Can the shared data and rules be expressed with Platform identities, contracts, documents, indexes, tokens, or NFT ownership?
3. Is the information appropriate for replicated, queryable state?

Those questions lead to practical choices:

- A checkout or peer-to-peer payment app can benefit directly from Core payments and fast transaction locking.
- A membership app can combine identities, usernames, verifiable membership documents, and a fungible rewards token.
- A collectible marketplace can use document-based NFTs for unique ownership and purchase behavior.
- A medical-record system should not place plaintext patient records on Platform. It might anchor a minimal proof while keeping encrypted records under an appropriate private-data system.
- A computation-heavy protocol that requires arbitrary user-deployed programs is not a fit for Platform alone.

The decision rule is simple: **use Dash where settlement or independently verifiable shared state creates real product value; use other systems where privacy, arbitrary computation, or unrestricted queries are the primary need.**
