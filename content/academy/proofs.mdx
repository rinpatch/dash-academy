## Learning objectives

By the end of this lesson, you will be able to:

- explain how a state proof connects query data to committed Platform state;
- distinguish inclusion proofs from non-inclusion proofs;
- describe how proof verification changes a light client's trust model; and
- identify what a valid proof does—and does not—guarantee.

## From a response to consensus state

A DAPI response can contain the value you requested, but receiving a value is not the same as verifying it. The server could be faulty, compromised, or simply behind the rest of the network.

Platform stores current state in **GroveDB**, a hierarchical authenticated data structure. Changing any committed value changes the affected hashes up to one aggregate root. After Platform executes a block, that state-tree root is committed in the block header as the **AppHash**.

When a query requests a proof, the response provides enough cryptographic material to connect the result to that commitment:

1. A **GroveDB proof** contains the requested data—or evidence of its absence—and the hashes needed to reconstruct the relevant authenticated tree result.
2. The verifier checks that result against the state root committed as the block header's AppHash.
3. The verifier also needs valid Long-Living Masternode Quorum (LLMQ) context to authenticate the commitment instead of accepting a block identifier, root, or quorum key supplied only by the responding server.

Together, those checks connect the query result to authenticated consensus state. A changed value, substituted path, mismatched AppHash, invalid signature, or invalid quorum context breaks verification.

<Callout type="info" title="Proof formats are versioned">
Older Platform documentation describes separate `storeTreeProof` and `rootTreeProof` fields. The pinned WASM SDK exposes a current proof object with `grovedbProof`, quorum metadata, a signature, a round, and `blockIdHash`. Those field lists do not by themselves specify the exact signed message, so application code must use a verification implementation whose procedure is documented and validated for that proof version rather than inventing a manual signature procedure from field names.
</Callout>

<Callout type="info" title="Proofs authenticate a result, not a server">
A valid proof says, “this value or absence matches the consensus state committed at this block.” It does not say, “this DAPI server is always honest.”
</Callout>

## Inclusion and non-inclusion

State proofs answer two different questions.

| Proof | What it establishes | Example |
| --- | --- | --- |
| **Inclusion** | The returned key and value exist, without modification, in the proved state. | An identity with this ID has this public state. |
| **Non-inclusion** | The queried key does not exist in the proved state. | No document currently occupies this unique indexed value. |

An empty response alone does not prove absence: a server could omit a real value. A verified non-inclusion proof ties the absence to the authenticated tree state.

Both proof types are relative to a particular committed block. They concern finalized state, not pending changes and not the historical sequence of events that produced the current value.

## What changes for a light client

A full node can build state by processing the chain. A **light client** avoids that work. It can ask DAPI for the data and proof, reconstruct the state commitment locally, verify it against the block header's AppHash, and authenticate the committed block with valid validator-quorum context. Together, that authenticated block and its AppHash become the client's **authenticated consensus anchor** for the response.

That removes the responding DAPI node from the state-integrity trust boundary. The client does not need to assume that one server returned the correct value, and it does not need to replay every state transition.

Trust has not disappeared; it has moved. The client needs an authenticated source of the appropriate quorum public keys and block context. A Merkle path that matches a root supplied by the same untrusted server proves only internal consistency. Likewise, the presence of signature bytes and a quorum hash in a response is not verification: a documented, version-matched implementation must validate the proof and its consensus context.

The practical decision is therefore:

> **Verify the data path and authenticate the commitment it reaches.**

## Verification boundaries

Cryptographic verification is powerful because its guarantee is narrow and testable. Keep these boundaries explicit:

- **TLS and state proofs solve different problems.** TLS encrypts and protects the connection in transit. A state proof authenticates the returned Platform state. One does not replace the other.
- **Proof delivery is optional.** If a client does not request a proof, or receives one but does not verify it, the response has no proof-backed state guarantee.
- **A proof is tied to committed state.** It proves a value or absence at the referenced block. It does not reveal pending changes or the history that led there. The client must also decide whether its authenticated block context is sufficiently current for the application.
- **Consensus is not real-world truth.** A proof can show that Platform committed a profile field or marketplace claim. It cannot show that the person or claim is genuine, desirable, or useful.
- **Verification does not create availability.** A proof can authenticate a response that arrives; it cannot force a server or the network to answer.
- **Failure means unverified.** If the path, AppHash, quorum signature, or required context fails verification—or is missing—the client must treat the response as unverified. Accepting the payload anyway crosses the verification boundary.

<Callout type="warn" title="Never downgrade silently">
If proof verification fails, do not display or process the payload as valid Platform state. Retry through another endpoint, refresh the trusted block context, or report that the response could not be verified.
</Callout>
