## Learning objectives

By the end of this lesson, you will be able to:

- explain how a data contract validates an application's documents;
- model records as document types with required and optional fields;
- connect indexes and their property order to supported queries; and
- identify the decisions and execution boundaries fixed at contract time.

## A contract is the application's data agreement

A **data contract** is a registered description of the data an application may store on Dash Platform. It groups one or more named document types and gives each type a schema. When an application creates or changes a document, Platform checks the data against that schema. A write that does not conform is rejected.

The identity that registers a contract owns it, and only that owner can update it. This is the bridge from the identities lesson: an identity is the actor, while its data contract defines the records that actor's application can use.

Think of the layers this way:

```text
owner identity
└── data contract
    ├── post document type
    └── profile document type
```

Each document is one record of exactly one named type. A `post` and a `profile` can have different fields, validation rules, indexes, and behavior while remaining in the same application contract.

## Schemas define valid documents

Document types use JSON Schema-style definitions. Properties declare field types and constraints; `required` lists fields that every document must contain. A declared field omitted from `required` is optional.

Here is a compact, illustrative `post` document type. It is a model to read, not registration code:

```json title="Illustrative post schema"
{
  "post": {
    "type": "object",
    "properties": {
      "authorId": { "type": "string", "position": 0, "maxLength": 44 },
      "slug": { "type": "string", "position": 1, "maxLength": 63 },
      "title": { "type": "string", "position": 2, "maxLength": 120 },
      "publishedAt": { "type": "integer", "position": 3, "minimum": 0 }
    },
    "required": ["authorId", "slug", "title", "publishedAt"],
    "additionalProperties": false,
    "indices": [
      {
        "name": "byAuthorAndPublishedAt",
        "properties": [{ "authorId": "asc" }, { "publishedAt": "desc" }],
        "unique": false
      },
      {
        "name": "uniqueSlug",
        "properties": [{ "slug": "asc" }],
        "unique": true
      }
    ]
  }
}
```

Four details are specific to a valid Dash contract:

- Every property at the same nesting level has a unique, sequential `position` starting at `0`. A nested object starts its own sequence.
- `additionalProperties` must be `false` wherever `properties` are defined. Documents cannot smuggle in fields the contract never described.
- Constraints such as `maxLength` and `minimum` are validation rules, not interface hints. Platform enforces them when a document is written.
- An indexed string property may have a maximum length of at most 63 characters. The indexed `authorId` and `slug` fields stay within that limit; the unindexed `title` can use a larger schema limit.

Schema validation answers **what may be stored**. It does not automatically make every field searchable.

## Indexes design the query paths

An index is an ordered lookup structure declared on a document type. Apart from Platform's documented primary-key handling for `$id`, fields used for filtering or sorting must be covered by a suitable index. Adding a property to the schema does not, by itself, make it queryable.

The example's indexes support two different needs:

| Index | Intended access pattern | Additional rule |
| --- | --- | --- |
| `byAuthorAndPublishedAt` | Find one author's posts in publication order | `authorId` is the leading property; `publishedAt` follows it |
| `uniqueSlug` | Find or enforce one post per slug | No two `post` documents may share the same non-null slug |

Property order matters in a compound index. Queries must follow the index's prefix and ordering rules. For `byAuthorAndPublishedAt`, the contract was designed around selecting an author first and then walking that author's publication times. It is not a general promise that any combination of those fields will work.

A unique index does two jobs: it provides a query path and enforces a data invariant when every indexed property is non-null. If any indexed property is null, Platform cannot enforce uniqueness for that document's indexed combination. In this example, `slug` is required and has the `string` type, so every valid post supplies a non-null slug and the unique index prevents duplicates. If uniqueness matters to the application, deciding it in the contract is stronger than checking for duplicates only in client code.

<Callout type="info" title="Design indexes from questions">
Write down the questions the application must answer—such as “show this author's newest posts”—then design indexes for those access patterns. Indexes are part of the model, not a performance switch to add casually afterward.
</Callout>

## Decisions to make before registration

Contract design makes several choices durable. Before registering a contract, make these **contract-time decisions**:

- **Document boundaries:** which concepts deserve separate document types;
- **Field shape:** types, constraints, property positions, and required versus optional data;
- **Behavior:** whether documents may be updated, transferred, or deleted;
- **Invariants:** which field combinations must be unique; and
- **Access patterns:** which filters and sort orders need indexes.

Contracts can evolve, but compatibility limits make the initial model important. Updates can add document types, optional properties, and some non-unique indexes. Removing or renaming fields, changing existing field types, or altering existing unique indexes is restricted because stored documents and query structures already depend on them.

This makes optional fields useful for anticipated growth. It also makes speculative unique indexes risky: uniqueness is an enduring rule, not merely an optimization.

## What contracts do not execute

A data contract validates and indexes data. It is not a place to upload arbitrary server-side application logic.

### No developer-defined triggers

Application developers cannot deploy custom data triggers such as “when a post is saved, automatically update a counter.” Dash Platform does contain hard-coded triggers, but those are protocol logic used only by system contracts. Saying “no triggers” for application design means **no custom triggers supplied by ordinary contract authors**.

Put application workflows in client or service code, and submit each intended state change explicitly.

### No server-side joins

A regular document query names one `dataContractId` and one `documentTypeName`. It can filter, order, limit, and paginate that one source, but it has no second document source or join clause. Grouping is available only for aggregate count, sum, and average queries; it is ignored when fetching documents normally.

To relate a `post` to a `profile`, store an application-defined identifier field such as `authorId`, fetch the matching profile separately, and combine the results in the application. For read-heavy views, an application may deliberately copy selected display data into another document type, but then it owns the consistency work. An identifier field is not a relational foreign key, and the contract will not join or cascade changes for you.

## What you accomplished

You can now sketch document types with valid field schemas, choose indexes from real query paths, and identify which invariants and behaviors belong in the contract. You also know where the contract stops: application code coordinates workflows and relationships because developers cannot add custom triggers or server-side joins.
