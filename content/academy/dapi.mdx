## Learning objectives

By the end of this lesson, you will be able to:

- describe what DAPI is and why its being decentralized matters for an application that depends on it;
- choose the right part of DAPI for a Dash Core need versus a Dash Platform need; and
- select the DAPI instance your client talks to, and explain why falling back to a different instance is safe.

So far you have met the two layers of Dash, identities, data contracts, and documents. This lesson is about the front door your application uses to reach all of it.

## What DAPI is

DAPI is Dash's decentralized API — the acronym is where the name comes from. It is a decentralized HTTP API that exposes <Term id="json-rpc">JSON-RPC</Term> and <Term id="grpc">gRPC</Term> endpoints, which your application calls the way it would call any backend service.

Two properties set it apart from a typical web API:

- **It is decentralized.** Instead of one company running one server, DAPI is served by Dash's <Term id="masternode">masternode</Term> network — specifically the <Term id="evonode">evonodes</Term>, the masternodes that run Dash Platform. Many nodes across the network operate the same API, so there is no single point of failure and no single operator you have to trust.
- **It gives you node-level access without hosting a node.** DAPI provides the same access and security you would get from running your own Dash node, but without the cost and maintenance of hosting one.

DAPI encrypts its connections with TLS, so your traffic is protected in transit.

<Callout type="info" title="A useful mental model">
DAPI is to Dash what a hosted JSON API is to a traditional database — except no single company runs it, and it spans both halves of the network.
</Callout>

## One access point for Core and Platform

DAPI presents a single interface that gives you access to both of Dash's layers. That mirrors the two jobs from the first lesson: Dash Core moves money on layer 1, and Dash Platform stores and verifies application data on layer 2.

DAPI exposes those two layers through two kinds of endpoints:

- **<Term id="json-rpc">JSON-RPC</Term>** exposes some layer-1 information about Dash Core. Think of it as a read-only window onto the Core chain — for example, `getBestBlockHash` and `getBlockHash`.
- **<Term id="grpc">gRPC</Term>** is the workhorse. It serves Dash Platform — the layer-2 data layer — and also Dash Core, including streaming: DAPI can push you live events about new blocks and masternode-list updates as they happen.

The Platform half of gRPC lets your app read and change Platform state — for example, `getIdentity`, `getDataContract`, and `getDocuments` for reads, and `broadcastStateTransition` with `waitForStateTransitionResult` for writes. The Core half covers operations such as broadcasting a transaction or subscribing to a live stream of updates.

| Your app needs to… | Use |
| --- | --- |
| Read some Dash Core chain information | <Term id="json-rpc">JSON-RPC</Term> |
| Query identities, contracts, or documents | <Term id="grpc">gRPC</Term> (Platform) |
| Broadcast a transaction or subscribe to Core updates | <Term id="grpc">gRPC</Term> (Core) |

Platform gRPC responses can also return cryptographic proofs that let you check the returned data was not tampered with — that is the topic of the next lesson.

## Choosing a DAPI endpoint

There are two separate choices wrapped up in endpoint selection, and it helps to keep them apart.

First, the **endpoint family** — the choice you just made above. Is this a JSON-RPC or a gRPC call, and within gRPC, is it a Core operation or a Platform operation? That decision follows from *what operation* you are performing.

Second, **which DAPI instance** to talk to. Because many masternodes serve the same API, your client has a choice here too. A client selects an instance by:

- a **network name** — `testnet`, `mainnet`, or `local`; or
- an explicit **seed list or URL**, such as the public testnet seed `seed-1.testnet.networks.dash.org` on port `1443`.

Because the same API is served by many nodes, if one instance becomes unavailable your client can fall back to a different one. That is what "no single point of failure" means in practice: a node going offline does not stop your application.

This lesson stays conceptual on purpose. The actual SDK calls for connecting — constructing a client, pointing it at <Term id="testnet">testnet</Term>, and making a read — come in module 8. For now, the takeaway is that choosing an endpoint means both picking the right endpoint family for the operation and letting your client choose among the many DAPI instances that serve it.
